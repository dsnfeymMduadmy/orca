# Orca OS — Архитектура

## 1. Железо и карта памяти

Плата: STM32H743IIT6 (Cortex-M7 @480MHz), LQFP176.

| Память                | Объём   | Назначение                                                     |
|-----------------------|---------|----------------------------------------------------------------|
| Internal FLASH        | 2 MB    | Ядро Orca OS (kernel, FreeRTOS, HAL, loader, GUI-движок)       |
| DTCM RAM              | 128 KB  | Стеки задач ядра, критичные к латентности данные               |
| AXI SRAM              | 512 KB  | Куча ядра, framebuffer(ы), очереди/буферы                      |
| SRAM1/2/3/4           | ~288 KB | DMA-буферы периферии (SDMMC, SPI, I2C, USB)                    |
| Backup SRAM           | 4 KB    | Данные, живущие через reset (без VBAT — best effort)           |
| Внешняя QSPI FLASH    | 16 MB   | Ресурсы ОС "из коробки": шрифты, иконки, дефолтные апки,       |
|                       |         | резерв под будущий OTA-образ ядра                              |
| Внешняя SDRAM (FMC)   | 32 MB   | Арена времени выполнения модулей/приложений с SD, кучи GUI     |
| I2C EEPROM            | —       | Настройки устройства, калибровка, Wi-Fi/BLE креды              |
| microSD (SDMMC1)      | —       | `/modules`, `/apps`, `/system`, `/res` — пользовательский слой |

Ключевая идея: **всё, что "тяжёлое" и часто меняется (модули, приложения, их ресурсы) — на SD.
Ядро, драйверы и системные сервисы — во внутренней флеш-памяти**, которой достаточно и она надёжнее SD.

## 2. Слои системы

```
┌─────────────────────────────────────────────┐
│  Apps (SD:/apps/*)         — GUI-приложения │
├─────────────────────────────────────────────┤
│  Modules (SD:/modules/*)   — драйверы железа│
│  по запросу (ESP, RFID, BLE-донглы и т.п.)  │
├─────────────────────────────────────────────┤
│  Orca API (syscall table)  — стабильный ABI │
├─────────────────────────────────────────────┤
│  OrcaKernel                                 │
│   ├─ App/Module Manager (loader + lifecycle)│
│   ├─ VFS (FatFS: SD + QSPI + EEPROM)        │
│   ├─ GUI engine (framebuffer, widgets)      │
│   ├─ Board HAL (LCD, touch, buttons, power) │
│   └─ FreeRTOS (планировщик, IPC, таймеры)   │
├─────────────────────────────────────────────┤
│  CMSIS / STM32H7 HAL / LL drivers           │
└─────────────────────────────────────────────┘
```

## 3. Модель загрузки модулей/приложений

Модуль/приложение — это **relocatable ELF32** (компилируется как `-r`/partial-link объект,
без ОС-зависимостей, кроме таблицы API Orca). Подход аналогичен Flipper Zero FAP.

Пайплайн:

1. При старте (или по запросу пользователя из GUI) `AppManager` сканирует `SD:/modules` и
   `SD:/apps`, читает `module.json` / `app.json` (манифест: имя, версия, точка входа,
   требуемые ресурсы, иконка).
2. По запросу на запуск `Loader`:
   - открывает `.orca` (ELF32) файл через VFS,
   - парсит ELF header, секции `.text/.rodata/.data/.bss`, таблицу символов,
   - выделяет память **в SDRAM** под код+данные (арена, см. §4),
   - копирует/загружает секции, обнуляет `.bss`,
   - резолвит внешние символы **только** через таблицу `orca_api_t` (никакого прямого
     доступа к HAL/FreeRTOS/памяти ядра — изоляция по конвенции, т.к. MPU-защита это
     будущая задача, см. TASKS.md),
   - применяет релокации (`R_ARM_ABS32`, `R_ARM_REL32`, `R_ARM_TARGET1`,
     `R_ARM_THM_CALL`, `R_ARM_THM_JUMP24`) — BL/BLX перекодируются побитово в
     `patch_thumb_branch()`, поэтому `-mlong-calls` в SDK модулей больше не нужен
     и убран: межфункциональные вызовы идут прямым `BL`, а не через литералы
     в памяти,
   - вызывает экспортированную `orca_app_main(const orca_api_t* api)`.
3. Модуль/приложение исполняется в **своей FreeRTOS-задаче** со своим стеком (в SDRAM),
   что даёт вытесняющую многозадачность и защиту от подвешивания системы одним модулем.
4. Остановка: kernel вызывает `orca_app_stop()` (если экспортирован) → таск удаляется →
   память арены освобождается через простой bump/free-list allocator.

## 4. Арена SDRAM

32 MB SDRAM делится (ориентировочно, тюнится в `orca_memmap.h`):

- 4 MB — framebuffer(ы) GUI (double buffering для RGB-дисплея),
- ~2 MB — куча GUI-движка (виджеты, кэш изображений),
- ~26 MB — арена загрузки модулей/приложений (heap-пул с allocator'ом кернела),
  каждый загруженный модуль получает свой блок (код+данные+стек задачи).

## 5. Два дисплея

- **LCD1 (40-pin, RGB)** — основной экран (аппаратный LTDC контроллер H7), высокое разрешение,
  используется GUI-движком как основной framebuffer.
- **LCD2 (20-pin, SPI + I2C touch)** — вспомогательный/альтернативный экран (напр. для более
  простого UI или второго форм-фактора корпуса). Драйвер регистрируется как второй
  `orca_display_t` в HAL, GUI может рендерить в один из них или в оба.

## 6. Файловая система SD-карты

```
/system/            — конфиг устройства, логи, реестр установленных модулей/приложений
  config.json
  logs/
/modules/
  <module_name>/
    module.json     — манифест
    module.orca     — relocatable ELF
    README.md
/apps/
  <app_name>/
    app.json
    app.orca
    assets/         — иконки, спрайты, шрифты приложения
/res/
  fonts/            — общесистемные шрифты (fallback, если нет на QSPI)
  icons/
```

## 7. Отладка

- CH340 (USB-UART) — маппится на системную консоль (shell, printf-лог, ISP-загрузка).
- SWD (4 pin, 2.0mm) — штатная отладка/прошивка через ST-Link/J-Link.

## 8. Безопасность/устойчивость (в рамках defensive-подхода)

- Загружаемый код рассматривается как untrusted: обязательна проверка контрольной суммы/подписи
  манифеста перед запуском (см. TASKS.md — код-signing — будущая задача).
- Нет прямого доступа модулей к памяти ядра — только через API-таблицу.
- Watchdog (IWDG) следит за живостью системных тасков; зависший модуль не должен ронять весь стек.
